# PostgreSQL / Supabase — configuração e validação

## Configuração

Use uma connection string PostgreSQL do Supabase em `ConnectionStrings__DefaultConnection` (Railway). Mantenha SSL habilitado (`SSL Mode=Require`) e guarde credenciais somente em variáveis privadas. Nunca registre a connection string nos logs.

A aplicação escolhe o provider Npgsql quando a connection string começa com `Host=`, `postgres://` ou `postgresql://`. Em produção, a inicialização falha se SQLite for selecionado. O volume Railway `/data` persiste apenas as chaves do ASP.NET Core Data Protection.

## Inicialização

Em um banco Supabase vazio, `PostgresDatabaseBootstrapper` gera o DDL usando o modelo corrente do EF Core/Npgsql, cria as tabelas e registra as migrations históricas como baseline. Esse caminho não executa as migrations SQLite antigas sobre PostgreSQL. Se o schema já tiver tabelas mas não possuir histórico EF, a inicialização para sem sobrescrever os dados.

Migrations futuras devem ser provider-neutral sempre que possível. Para operações realmente específicas, verifique `ActiveProvider` e mantenha um ramo Npgsql e outro SQLite. Não compartilhe SQL SQLite com PostgreSQL.

## IDs

As chaves `int` devem usar geração automática (`ValueGeneratedOnAdd`, convenção EF Core). Npgsql materializa `GENERATED BY DEFAULT AS IDENTITY`; SQLite usa seu mecanismo de chave inteira. Não defina IDs manualmente em dados de seed, pois isso pode deixar a sequência/identity do PostgreSQL atrás do maior valor já inserido.

## Testes

Requisitos: .NET SDK 10 e uma instância PostgreSQL descartável.

```bash
export EASYVAN_TEST_POSTGRES='Host=localhost;Port=5432;Database=easyvan_test;Username=postgres;Password=postgres'
dotnet restore "Gerenciamento de Van.csproj"
dotnet build "Gerenciamento de Van.csproj" --configuration Release
dotnet test "tests/EasyVan.Tests/EasyVan.Tests.csproj" --configuration Release
```

O workflow GitHub Actions inicia PostgreSQL 16 e injeta `EASYVAN_TEST_POSTGRES`. Os testes validam o DDL do modelo, geração real de IDs e geração do script de migrations pelo provider Npgsql. Sem essa variável, os testes de integração retornam sem executar; por isso a execução no CI é obrigatória para liberar produção.

## Checklist de deploy

1. Verificar CI verde para o commit exato.
2. Revisar o script de migrations PostgreSQL gerado e confirmar o estado de `__EFMigrationsHistory`.
3. Fazer backup/snapshot do banco Supabase e validar em ambiente de homologação.
4. Conferir constraints, índices, permissões e RLS sem remover dados.
5. Só então autorizar o deploy na Railway. Não aplicar migrations manualmente diretamente no banco de produção sem plano de rollback.
